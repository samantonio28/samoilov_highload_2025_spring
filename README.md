# Tinder 
# 1. Тема и целевая аудитория
`Tinder` - сервис для онлайн-знакомств и планирования свиданий, имеющий клиенты на Android и IOS, а также веб-клиент. Учитывается геопозиция пользователей, интересы, а также применяется рекомендательная система на основе предыдущих действий пользователя. Главное действие - свайп, т.е. слистывание карточек других пользователей влево или вправо. На основании содержания карточки, в которой на фоне находится фото пользователя, а на переднем плане - информация о нём, такая как возраст, рост, местоположение, интересы, пользователь делает выбор: не понравилось - листает влево, захотелось пообщаться с этим человеком - листает вправо. В случае, если оба пользователя друг для друга выбрали свайп вправо, то у них появляется возможность в приложении пообщаться или найти место, чтобы пообщаться вживую.

## MVP
- Авторизация/Регистрация
- Заполнение профиля, редактирование профиля
- Взаимодействие с лентой карточек (просмотр данных + свайп)
- Установка фотографий 
- Общение в чате
- Выбор места для встречи
- Получение уведомлений о совпадениях

### Технические метрики

Хранилище используется для данных пользователя (карточки/профиля) и сообщений, а также о свайпах.

Расчёт среднего размера профиля: персональные данные пользователя, никнейм, контакты (суммарно 2 КБ). Для хранения фото выделяется 410 КБ (размер фото 640*640) пикселей. Есть возможность загрузить 5 фото.

Из этого следует, что на одного пользователя требуется выделить 2 КБ + 5 * 410 КБ = 2052 КБ -> на всех 530 млн пользователей потребуется 

`530 млн * 2052 КБ = 1012 ТБ`

Расчёт затрат на сообщения: примем, что длина сообщения равна 50 символам, а один символ весит 2 байта, тогда вес сообщения равен в среднем 100 байт. За один день пользователь отправляет 99 сообщений. Переписки хранятся ~ полгода, поэтому хранилище будет занимать

`42 млн * 99 * 100 байт * 180 дней = 68 ТБ`

Свайп - это булево значение, которое весит 1 байт. Предположим, что свайпы хранятся в течение года для улучшения алгоритмов и аналитики

`42 млн * 48 * 1 * 365 = 685.3 ГБ`

### 3.2 Схема балансировки
Для определения первоначального региона подключения используется Geo-based DNS. Этот метод оптимален для глобального сервиса, такого как Tinder, так как он автоматически направляет пользователя к кластеру серверов, находящемуся в ближайшем географическом регионе. Это позволяет минимизировать сетевую задержку и предотвратить перегрузку каналов связи, обеспечивая быстрый отклик приложения.
- Для более точной и отказоустойчивой маршрутизации внутри него применяется протокол BGP Anycast. Так как дата-центры Tinder раскиданы по всему миру, эта технология позволяет нескольким физическим дата-центрам в одном регионе объявлять один и тот же IP-адрес

# 4. Локальная балансировка нагрузки
### Схема балансировки
1) Выдан IP дата-центра по global-balancing
2) Трафик приходит на железо, называемое Local Traffic Manager.
3) В зависимости от вида трафика сделать следующее:
    - если веб-трафик, то LTM сам балансирует трафик на сервер
    - если мобильный трафик (а он преимущественный), то LTM балансирует трафик на nginx, который в свою очередь балансирует трафик на мобильный кластер по стратегии round-robin

LTM - железо, разработанное компанией F5, используемое в сервисах, аналогичных разрабатываемому. Также она предоставляет решение для глобальной балансировки.

### Решение по развертыванию - Kubernetes
Kubernetes, разработаннытй Google, - открытый контейнерный оркестратор, который позволяет развертывать и масштабировать приложения в кластере. Он позволяет автоматизировать процессы развертывания, обновления и отказоустойчивости приложений.
1) Создается Kubernetes Service, который будет действовать как балансировщик нагрузки для приложений. Service определяет маршруты к подам с использованием механизма Service Discovery.
2) Внутри кластера Kubernetes, kube-proxy будет перенаправлять трафик с Service на поды, используя стратегию балансировки sticky sessions.

### Нагрузка по терминации SSL
При такой схеме балансировки можно терминировать SSL на уровне nginx (с кешированием SSL-тикетов для улучшения производительности).  
Пиковый RPS равен 464 476.24, суммарный пиковый трафик - 2267.1432 Гбит/сек.  
Предположим, что на датацентр распределяется глобальной балансировкой примерно 20% трафика, тогда можно рассчитать среднюю нагрузку на каждый датацентр:

464 476.24 * 0.2 = 92895.248 RPS  
2267 * 0.2 = 441.8 Гбит/сек 

### Обеспечение отказоустойчивости
- несколько роутеров на входе в ДЦ
- несколько инстансов nginx
- следует выделить железо, способное выдержать б*о*льшую часть пикового трафика
- Проводить e2e health check-и каждые 30 секунд + availability check-и каждую минуту + проверки базы данных и кеша каждые 5 минут

# 7. Алгоритмы

### Система рекомендаций
В основе системы рекомендаций будет положен алгоритм Эло.

### Алгоритм Эло
Рейтинг Эло — это математический алгоритм, первоначально разработанный для шахмат, который оценивает относительную "силу" игроков на основе результатов их взаимодействий. В контексте Tinder алгоритм измеряет "привлекательность" пользователей и оптимизирует подбор пар для увеличения вероятности взаимных симпатий.

### Принцип работы
Алгоритм работает по принципу: если пользователь с высоким рейтингом лайкает пользователя с низким рейтингом — это ожидаемо, и рейтинги меняются незначительно. Если же пользователь с низким рейтингом лайкает пользователя с высоким рейтингом — это неожиданно, и рейтинги изменяются существенно.

#### Входные данные
1) Текущий рейтинг пользователя $A$ (инициатор свайпа)
2) Текущий рейтинг пользователя $B$ (объект свайпа)
3) Результат взаимодействия: лайк ($1$) или дизлайк ($0$)
4) Коэффициент $K$: параметр, определяющий скорость изменения рейтинга

#### Выходные данные
1) Обновленный рейтинг пользователя $A$
2) Обновленный рейтинг пользователя $B$

Шаг 1
--
Для двух пользователей с рейтингами $R_A$ и $R_B$ рассчитывается ожидаемая вероятность того, что пользователь A лайкнет пользователя B:

$P_A = \frac{1}{1 + 10^{\frac{R_B - R_A}{400}}}$

Эта формула гарантирует, что:
- eсли $R_A$ значительно выше $R_B$, вероятность $P_A$ близка к $1$
- если $R_A$ значительно ниже $R_B$, вероятность $P_A$ близка к $0$
- при равных рейтингах вероятность равна $0.5$

Шаг 2: Обновление рейтингов
--
После каждого свайпа рейтинги обновляются по формулам:

$R_{A новый} = R_A + K × (O_A - P_A)$  

$R_{B новый} = R_B + K × (O_B - P_B),$  

где:
- $O_A$ = $1$ (если лайк) или $0$ (если дизлайк)
- $O_B = 1 - O_A$ (симметричный результат)
- $P_B = 1 - P_A$ (симметричная вероятность)

### Алгоритм для Tinder:

Этап 1. Инициализация системы
--
1) Каждому новому пользователю присваивается начальный рейтинг (например, 1000)
2) Устанавливается коэффициент $K$ (оптимальное значение подбирается экспериментально)
3) Создается доп хранилище рейтингов пользователей (подойдет `PostgreSQL`)

Этап 2. Обработка свайпов
--
Для каждого свайпа выполняются следующие действия:
1) Извлечение текущих рейтингов: система получает текущие рейтинги обоих пользователей
1) Расчет ожидаемых вероятностей: вычисляется вероятность лайка для каждого пользователя
1) Обновление рейтингов: на основе фактического результата (лайк/дизлайк) пересчитываются рейтинги
1) Сохранение изменений: обновленные рейтинги сохраняются в системе

Этап 3. Генерация рекомендаций
--
При формировании ленты рекомендаций для пользователя:

1) Отбор кандидатов: система выбирает пользователей из того же региона, соответствующих предпочтениям

1) Ранжирование по вероятности мэтча: для каждого кандидата рассчитывается вероятность взаимного лайка:

$P_{мэтч} = P_{A\ лайкает\ B} × P_{B\ лайкает\ A}$

Cистема комбинирует:
1) Пользователей с близким рейтингом (высокая вероятность мэтча)
2) Некоторое количество пользователей с разным рейтингом (для обучения системы)
3) Формирование ленты: кандидаты сортируются по убыванию вероятности мэтча

Этап 4. Адаптация параметров
--
- Динамический коэффициент $K$ для новых пользователей используется больший для быстрой адаптации, для опытных - меньший
- Корректировка по активности: система учитывает количество взаимодействий пользователя
- Корректировка $K$ и $R$ происходит раз в день

Этап 5. Выбор пользователей, подходящих по расстоянию.
--
Первые 4 этапа отобрали людей без особых знаний о том, что интересно конкретно данному пользователю. На данном этапе будем учитывать факторы, которые ближе к пользователю: будем сортировать по близости к пользователю, затем по совпадению интересов (по проценту совпадений данных массива интересов пользователя А и пользователя В). Затем сделаем ещё чётче: будем стараться продвигать тех пользователей из предлагаемых, которые через одного человека (какого-то друга/подруги) знакомы с пользователем. 

### Алгоритм антиспама и детекции фейк-аккаунтов для Tinder

Этап 1. Предварительная верификация
--
**Валидация контактных данных:**
- Проверка номера телефона на принадлежность к виртуальным операторам
- Верификация email-адреса через отправку подтверждающего кода
- Анализ домена email на наличие в черном списке

**Анализ цифрового отпечатка:**
- Сбор данных об устройстве (ID, модель, ОС)
- Проверка на использование эмуляторов или VPN-сервисов

Этап 2. Мониторинг активности в реальном времени
--
Для каждого пользовательского действия выполняются следующие проверки:

1) Анализ паттернов свайпов:
    - Расчет скорости свайпов (норма: 1-20/мин, подозрительно: 50+/мин)
    - Определение соотношения лайков/дизлайков
    - Выявление механических паттернов (одинаковые интервалы)
2) Детекция спам-поведения:
    - Поиск идентичных сообщений, отправленных разным пользователям
    - Обнаружение URL-ссылок в первых сообщениях
    - Анализ времени ответа (мгновенные ответы = бот)

Этап 3. Оценка рисков и скоринг
--
#### Формирование оценки доверия к пользователю

Расчет показателей риска:
- ProfileScore: полнота и качество профиля (фото, описание, верификации)
- BehaviorScore: анализ паттернов поведения (свайпы, сообщения, активность)
- DeviceScore: репутация устройства и цифрового отпечатка

Комплексная оценка Trust Score:

```
TrustScore = 0.4 * BehaviorScore + 
             0.3 * ProfileScore + 
             0.3 * DeviceScore
```

Интерпретация результатов:
- 0-30% баллов: низкий риск 
- 30%-60% баллов: умеренный риск
- 60%-80% баллов: высокий риск
- 80%-100% баллов: критический риск (бан)

Обновление показателей:
- Ежедневный пересчет скоринга для активных пользователей
- Учет новых данных и изменений в поведении
- Корректировка весов на основе эффективности детекции

# 9. Обеспечение надёжности

Высокая доступность и отказоустойчивость критически важны для сервиса знакомств, где даже кратковременные сбои приводят к потере пользовательских взаимодействий и потенциальных совпадений. Архитектура надежности Tinder построена на принципах избыточности, автоматического восстановления и стратегической деградации функций.

## 9.2 Стратегии Graceful Degradation для Tinder

В отличие от мессенджеров, где основные функции (чат, голос) критичны, Tinder допускает стратегическую деградацию некритичных функций при сохранении core-функционала.

### 9.2.1 Сценарии частичных отказов

#### **Swipe Service недоступен (критичный сбой)**
**Приоритет: Критический** - влияет на основной user journey

**Бэкенд-действия:**
- Автоматическое переключение на read-only режим (показ ленты без возможности свайпов)
- Кэширование предвычисленных рекомендаций на 6 часов вперед в Redis
- Queue-based обработка: буферизация свайпов в Kafka с deferred processing
- Circuit breaker для зависимых сервисов (рекомендации, антиспам)

**Клиентский опыт:**
- Отображение сообщения: "Обновляем рекомендации, скоро вернемся!"
- Показ кэшированной ленты из Redis (последние 50 профилей)
- Сохранение локальных свайпов для последующей синхронизации

#### **Recommendation Service недоступен**
**Приоритет: Высокий** - влияет на качество рекомендаций

**Бэкенд-действия:**
- Fallback на простой алгоритм: географическая близость + базовые фильтры из DynamoDB
- Использование кэшированных рекомендаций из Redis (TTL 1 час)
- Приоритизация активных пользователей (online в последние 24 часа)
- Упрощенный ELO расчет без ML-факторов, используя только историю свайпов из DynamoDB

**Клиентский опыт:**
- Прозрачная деградация (пользователь не видит изменений)
- Незначительное снижение релевантности рекомендаций
- Сохранение базовой функциональности свайпов

#### **Media Service (S3/CDN) недоступен**
**Приоритет: Средний** - влияет на UX, но не на функциональность

**Бэкенд-действия:**
- Автоматическое переключение на резервный регион S3 через Cross-region replication
- Показ placeholder-аватаров (градиенты по user_id) генерируемых на лету
- Отключение загрузки новых фото с сохранением черновиков в локальном кеше
- Приоритетная отдача текстового контента из DynamoDB

**Клиентский опыт:**
- Отображение градиентных аватаров вместо фото
- Возможность свайпов по текстовой информации
- Сохранение черновиков фото для загрузки позже

#### **Chat Service частичная деградация**
**Приоритет: Средний** - влияет на communication после мэтча

**Бэкенд-действия:**
- Read-only режим для истории сообщений из DynamoDB
- Offline-сообщения через push-уведомления с сохранением в очереди Kafka
- Queue-based отправка с гарантированной доставкой через Kafka persistence
- Упрощенная синхронизация через REST polling вместо WebSocket

**Клиентский опыт:**
- Показ истории переписки из локального кеша без возможности ответа
- Уведомления о новых сообщениях через push с локальным хранением
- Автоматическая синхронизация с DynamoDB при восстановлении

## 9.3 Асинхронная обработка и паттерны отказоустойчивости

### 9.3.1 Идемпотентная обработка свайпов
1. Проверка идемпотентности через Redis
2. Атомарная запись в DynamoDB с condition check
3. Запись идемпотентного ключа в Redis (TTL 24 часа)
4. Публикация события в Kafka для асинхронной обработки

Преимущества для Tinder:
- Гарантированная однократная обработка свайпов через DynamoDB conditional writes
- Предотвращение дублей совпадений через идемпотентные ключи
- Асинхронная обработка через Kafka с сохранением порядка в партициях
- Возможность реплеи событий при сбоях благодаря персистентности Kafka

### 9.3.2 Circuit Breaker для зависимых сервисов
Конфигурация для Recommendation Service с DynamoDB:
```yaml
circuit_breaker:
  recommendation_service:
    failure_threshold: 5          # 5 ошибок подряд
    success_threshold: 3          # 3 успеха для восстановления  
    timeout: 2000ms               # таймаут вызова DynamoDB
    fallback_strategy: "geographic_cached" # fallback на кэшированные рекомендации
    half_open_timeout: 30000ms    # 30 сек в half-open состоянии
    
  dynamodb_connections:
    max_connections: 1000         # лимит соединений к DynamoDB
    health_check_interval: 30s    # проверка доступности DynamoDB
    fail_fast: true               # быстрый отказ при недоступности
```

# 11. Расчёт ресурсов

Расчет ресурсов основан на пиковых нагрузках, определенных в главе 2, с учетом требований к отказоустойчивости (схема N+1) и эмпирических данных о производительности выбранных технологий. Все расчеты приведены для одного дата-центра с учетом распределения 20% общей нагрузки.

## 11.1. Расчет для сервисов (Stateless, Kubernetes)

Основной метрикой для stateless-сервисов является RPS. Для Go-сервисов, оптимизированных для высоких нагрузок, принимаем эмпирическое значение **~1500 RPS на одно ядро CPU**.

**Методика расчета:**
- `Требуемые ядра = ceil(Пиковый RPS сервиса / 1500)`

## 11.3. Расчет для систем хранения данных (Stateful)

### Amazon DynamoDB
**Модель расчета:** Provisioned Capacity Units (оплата за выделенную производительность)

**Read Capacity Units (RCU):**
- Пиковое чтение: 82,180 RPS
- Средний размер элемента: 4 КБ
- Пропускная способность: `82,180 × 4 KB = ~321 MB/s`
- Требуемые RCU: `~2600 единиц` (1 RCU = 1 строгий consistent read в секунду для элемента до 4 KB)

**Write Capacity Units (WCU):**
- Пиковая запись: 69,444 RPS  
- Средний размер элемента: 1 КБ
- Требуемые WCU: `~560 единиц` (1 WCU = 1 write в секунду для элемента до 1 KB)

**Обоснование:** Provisioned capacity обеспечивает предсказуемую производительность при пиковых нагрузках

### Redis Cluster
**Назначение:** Хранение сессий, кэш профилей, временные данные чатов

**Расчет объема памяти:**
- Сессии: 7.9 ГБ (126 млн записей × 66 байт)
- Кэш профилей: ~30 ГБ (горячие профили 10% пользователей)
- Кэш сообщений: ~50 ГБ (активные чаты)
- **Итого:** ~90 ГБ × 3 (репликация) = **270 ГБ RAM**

**Расчет производительности:**
- Пиковое чтение: ~82,000 RPS
- Производительность узла: 50,000-100,000 RPS
- **Конфигурация:** 6 узлов (3 мастера + 3 реплики)
- **Вычислительные ресурсы:** 8 vCPU на узел → **48 vCPU**

**Обоснование:** 6-узловой кластер обеспечивает отказоустойчивость и горизонтальное масштабирование

### Elasticsearch
**Назначение:** Полнотекстовый поиск пользователей  
**Объем данных:** 6.2 ГБ (таблица UserSearch)  
**Конфигурация:** 3 ноды (master-eligible + data)  
**Ресурсы на ноду:** 4 vCPU, 8 ГБ RAM  
**Итого:** **12 vCPU, 24 ГБ RAM**  
**Обоснование:** Небольшой кластер обеспечивает избыточность для критически важного функционала поиска  

### Amazon S3
**Назначение:** Хранение медиафайлов (фото, аватары, вложения)

**Расчет объема:**
- Профили: 1012 ТБ (5 фото × 410 КБ × 400 млн пользователей)
- Сообщения: 68 ТБ (вложения)
- Свайпы: 685 ГБ (метаданные)
- **Итого:** **~1080 ТБ**

**Сетевой трафик:**
- Пиковый исходящий трафик: ~700 Гбит/с
- **Особенность:** S3 автоматически масштабируется под нагрузку
